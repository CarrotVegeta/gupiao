# 股票持仓看板

这是一个用于个人跟踪持仓、分组、成本和实时行情的本地 Web 应用。

它是个人记录工具，不是投资建议。

## 本地运行

先安装依赖：

```bash
npm install
```

启动本地开发环境：

```bash
npm run dev
```

然后打开：

```text
http://localhost:5174
```

## 常用校验命令

```bash
npm run typecheck
npm test
npm run build
```

## 本地烟雾测试

建议按下面流程做一次完整验证：

1. `npm run dev`
2. 打开 `http://localhost:5174`
3. 新增股票 `600519`，也可以输入“贵州茅台”并从搜索候选中选择
4. 开仓价和持有数量可以留空；留空时股票会作为观察项保存
5. 需要计算收益时，编辑股票补录开仓价 `160` 和数量 `100`
6. 确认页面显示服务器返回的行情，或者显示“暂无行情/不可用”的可见状态
7. 页面顶部确认“大盘概览”可见，且指数卡片显示涨跌额 / 涨跌幅
8. 点击“涨停聚焦”，确认涨停表格可见，并包含“连板”和“板块”列；每行末尾有“添加自选”，点击后该行按钮置灰成“已在自选”，顶栏“自选”计数 +1
9. 确认四个子页签顺序是“涨停池 / 冲刺涨停 / 今/昨对比 / 连板天梯”；切到“今/昨对比”，确认一个板位一块、块头有家数与晋级率、块内上半是今天晋级到下一板位的票、下半是断板票（一档全断板时上半写“无”），涨幅都是今天的实时值；再切到“连板天梯”，确认今日池子按板位分层（最高板默认展开、其余折叠），统计条给出全部 / 首板 / 2 板 / 晋级率
10. 点击“竞价”，确认展示上一交易日涨停股、09:25 固定竞价结果、每只票的“竞价高开 / 竞价量比”两个条件（各带 ✓/✗）、“合格 / 不合格 / 数据不足”结论、“溢价”分档，以及盘中实时的“涨跌幅”列；量比 ≥10% 的额外显示“爆量”；09:15 之前（开盘集合竞价还没开始）确认“竞价日”显示的是上一交易日
11. 确认竞价列表优先按“合格”，再按昨日连板数、竞价量比从高到低排列
12. 切回“持仓”，确认“持仓分组”、收益率和“添加股票”入口仍然可见
13. 刷新页面
14. 确认持仓和备注仍然保留
15. 停止开发进程

## 数据保存

- 持仓、分组和备注都会保存在浏览器的 `localStorage` 中
- 本地存储键名为 `stock-dashboard:v1`
- 清空浏览器站点数据会清除这些记录
- 如果本地数据损坏，应用会自动恢复为默认状态

## 行情说明

- 页面行情由本地服务端接口 `/api/quotes` 提供
- 股票搜索由本地服务端接口 `/api/stock-search` 提供
- 服务端会再去请求公开行情源，因此查询行情需要网络可用
- 如果公开行情源在非交易时间或服务窗口外不可用，页面可能显示上一轮行情、过期行情或不可用状态

### 行情源：腾讯优先，东财兜底

`push2.eastmoney.com` / `push2his.eastmoney.com` 在部分网络会被上游**直接断连**，
这正是「行情大片缺失」的根因：个股行情、批量行情、大盘指数原先全部走 push2，一挂就全挂。

同一台机器、同一时刻各打 8~15 次（`npx tsx scripts/_host-health.ts`，结果见 `scripts/output/host-health.json`）：

| 上游 | 成功率 | p50 | 说明 |
| --- | --- | --- | --- |
| 东财 `push2` 单只/批量行情、`push2his` 日K | **0% ~ 25%** | — | `UND_ERR_SOCKET` / `RemoteDisconnected` |
| 东财 `push2delay` 批量行情、分笔明细 | 100% | ~46ms | 与主站同秒的**实时**镜像，不是延时行情 |
| 东财 `push2ex` 涨停池/强势池 | 100% | ~51ms | |
| 东财 `datacenter` 龙虎榜、`searchapi` 搜索 | 100% | ~53ms | |
| 腾讯 `qt.gtimg.cn` 单只/批量行情 | 100% | ~50ms | 返回 **GBK**，须用 `TextDecoder('gbk')` 解码，否则股票名乱码 |
| 腾讯 `ifzq` 日K / `stock` 分笔 | 100% | ~60ms | |
| 腾讯 `smartbox` 搜索建议 | 100% | ~58ms | |

因此行情链路改成：**腾讯 `qt.gtimg.cn` 优先 → 东财 `push2delay`（镜像）兜底 → `push2` 最后**。

| 数据 | 主源 | 备用源 |
| --- | --- | --- |
| 个股行情 `/api/quotes` | 腾讯 `qt.gtimg.cn`（批量 50 只/次） | 东财 `push2delay` → `push2` |
| 大盘指数 `/api/market-overview` | 腾讯 `qt.gtimg.cn`（带 sh/sz 前缀，`000001` 才能区分上证指数与平安银行） | 东财 `push2delay` → `push2` |
| 观察板块判定 `/api/watch-check` | 腾讯 `qt.gtimg.cn` + `ifzq` 日K | — |
| 股票搜索 `/api/stock-search` | 东财 `searchapi`（15/15 正常，未改） | — |
| 涨停池 / 强势池 / 龙虎榜 | 东财 `push2ex` / `datacenter`（一直稳定，未改） | — |
| 竞价链路 `/api/auction` | 腾讯 `stock.gtimg` 分笔（竞价价 + 量能）+ 东财 `push2ex` 池 | 东财 `push2delay` 分时（量能兜底 + 竞价过程形态）→ 批量报价拿今开；腾讯 `qt` 报价 / `ifzq` 交易日历 |
| 当日分时图 `/api/minute` | 腾讯 `ifzq.gtimg.cn/appstock/app/minute/query`（**一次一只票**，并发 6） | — |
| 情绪补充（封板率 / 高开率 / 获利率 / 连板梯队） | 财联社 `x-quote.cls.cn/v2/quote/a/stock/emotion`（仅当天，见下） | — |
| 板块轮动 `/api/themes/rotation` | 财联社 `x-quote.cls.cn/v2/quote/a/plate/rotation`（近 4 / 30 日 top10） | — |

响应里的 `source` 字段标明实际用了谁：`tencent`（全腾讯）、`eastmoney+tencent`（部分票由东财补齐）、
`eastmoney`（腾讯整批失败、全部走东财）。**已由东财补上的票不会留在 `errors` 里**，
否则前端会把它标成过期行情。

## 竞价筛选说明

- 候选范围为上一交易日收盘仍在涨停池内的股票
- 今日数据固定使用 09:25 集合竞价价格，不使用盘中最新价替代
- **09:15 之前整张卡退回上一个完整竞价日**：开盘集合竞价 09:15 才开始接单，在那之前行情源里的今开、
  分笔、大盘缺口还都停在上一个交易日，按今天算会得到「池子是昨天、价格是昨天、日期写今天」的卡。
  所以此时「竞价日」= 上一交易日、「昨日涨停」= **它的**上一交易日涨停池，价格/量比/溢价也正好都是那一天的 09:25，
  整张卡自洽。09:15 一到自动切回当天（09:15~09:25 当天还没有 09:25 成交，会先显示「缺少 09:25 竞价成交数据」）。
  这份回退快照在开盘前不会再变，服务端按「缓存到 09:15」处理，到了点自然过期、不用等 5 分钟；
  请求历史日期不受这条规则影响
- **合格判定只看两个条件（2026-09-18 起）**：两条都满足才显示「合格」，其余一律「不合格」。
  阈值集中在 `src/lib/auction-policy.ts`，前后端共用。
  1. **竞价高开幅度** `2% ≤ 涨幅 ≤ 6%`
  2. **竞价量比** `竞价成交额 ÷ 昨日全天成交额 ≥ 5%`（达到 10% 额外标「爆量」）
- 不再输出「收盘封板概率」，也不再按概率分档。原来的分组逻辑回归保留在
  `server/auction/model.ts` 供离线研究，线上判定不再调用它。
- 竞价成交额或昨日成交额缺失时算不出量比，直接判「数据不足」，不猜测。
  腾讯分笔拿不到量能时依次回退：**分时首个有量点** → 东财分笔明细 → 批量报价「今开」（只有价格）。
- 排序：合格在前 → 昨日连板数降序 → 竞价量比降序 → 代码。
- **竞价分时形态（2026-09-18 起，只观察不判定）**：新增一列展示 09:15~09:24 的**虚拟匹配价迷你走势**
  与一句话形状描述。这些形态**不参与合格判定**，因为它同样没有历史样本可回测。
  - `竞价走高/走低/走平 X%`：首点到尾点的方向
  - `尾段下砸 X%` / `尾段上抬 X%`：竞价成交价相对 09:24 虚拟匹配价的偏移
  - `摸板未封`：竞价过程中虚拟匹配价摸到过涨停价，但最终没封在上面
  - `后段放量(HH:MM)`：虚拟匹配量峰值落在 09:23 之后
  阈值集中在 `server/auction/minute.ts` 的 `AUCTION_TREND_THRESHOLDS`。
  形态与量能来源（`tick` / `minute`）一并写进 `data/auction-snapshots.jsonl`，`minuteTrend` 字段
  只在当天快照里有值，攒够交易日后再回来验证这类因子。
- **阈值是经验规则，尚未在本地历史样本上验证**：09:25 竞价量能没有可用的免费历史接口
  （腾讯分笔/同花顺分时忽略日期参数、东财 push2his 断连、网易 502）。每次成功返回都会把
  09:25 字段落到 `data/auction-snapshots.jsonl`，攒够交易日后再回测这两个阈值。
  2026-09-18 补充调研（见 [外部数据源调研](docs/thsdk-evaluation.md)）：**腾讯分时的第一个点、
  东财分时首个成交量不为 0 的点，就是 09:25 集合竞价**（47 只逐只对照，价格 47/47 完全相等、
  成交额最大误差 0.06%），已接成量能兜底来源；但两家分时同样只给最近一个交易日，
  **历史量能依旧拿不到**。
- 判定不再使用炸板家数和大盘缺口，因此也去掉了这两个上游请求。
- “竞价未涨停”按实际涨停价判断，只表示价格位置；不保证成交或盈利。
- 溢价标签仅描述价格位置，不参与合格判定。
- 盘中涨跌幅继续来自独立行情，不进入 09:25 固定快照。

### 「可买到 + 较高概率」的胜率天花板

2026-09-18 的补充研究：竞价未封板（买得到）的「较高概率」池，走前验证的真实封板率是
**52.7%**（529 条，3.81 只/天），池内次日开盘卖出平均 **-0.80%**。阈值往上扫到 p≥0.65
封板率仍在 52%~56%，排序在头部已经饱和。

- 加/减因子都提不动：5 个现有特征逐一剔除、再加 26 个单因子、10 个横截面/题材因子、
  6 组交互，共 36 个变体，AUC 全在 77.03%~77.69% 之间，无一构成改善。
- 唯一有信息量的是竞价涨幅，而它就是要付的买入价。
- 能提高封板率的只有把因子放到**筛选项**上：`昨日换手≥10% 且 概率≥0.5` →
  封板率 52.7%→65.7%（bootstrap 95% 区间 [+0.8, +26.4]，6/6 时间段为正）。
- 能改善收益的是 `竞价涨幅≤7%`：封板率不变，次日开盘收益 -0.80%→+0.19%。
- 唯一还没验证、且有实质空间的因子是 **09:25 竞价量能**（量比/竞昨比/竞价换手率）。
  腾讯、东财、网易、同花顺、新浪都拿不到历史 09:25 量能，只能从现在开始攒：
  `/api/auction` 每次成功返回都会把 09:25 字段按交易日写入 `data/auction-snapshots.jsonl`
  （见 `server/auction/snapshot-log.ts`，路径可用 `AUCTION_SNAPSHOT_FILE` 覆盖）。

完整研究与复现见 [竞价胜率研究](docs/auction-winrate-study.md)；
外部「竞价选股」规则的逐条核对见 [规则核验](docs/auction-rule-audit.md)。

### 旧版收益研究记录（非V2交易规则）

以下是旧数据与旧模型研究；包含事后按封板结果选择样本的统计，不能据此推导可执行买入收益或认定所有选股子集都无效。V2不采用下述买卖步骤作为交易规则。

同一批票、同样持有过夜，只在「什么时候买」上不同，结果完全相反（2026-02-26 ~ 09-16，不含手续费）：

| 入场方式 | 样本 | 次日开盘卖出 | t | 胜率 |
| --- | --- | --- | --- | --- |
| 竞价买入（今日 09:25 开盘价） | 9794 | **-0.41%** | -2.5 | 44% |
| 打板买入（当日封板后按涨停价）· 换手板 | 11450 | **+1.16%** | 14.3 | 58% |
| 打板买入 · 一字板（基本买不到） | 710 | +6.27% | 27.9 | 86% |

原因是涨停股的**次日高开溢价**：这个溢价是「持有涨停过夜」的报酬，竞价买入等于在次日替卖方承担它。
这组历史统计不足以证明所有选股子集均无效，仍需独立验证成交、入场与退出规则。

打板分档（只看买得到的换手板）：

| 分组 | 样本 | 次日开盘卖出 |
| --- | --- | --- |
| 首板 | 9571 | +1.05% |
| 2 板 | 1338 | +1.62% |
| 3 板 | 310 | +2.20% |
| ≥4 板 | 231 | +2.54% |

叠加 09:25 涨停概率模型后（候选池当天真的封板的那部分）：

| 分组 | 样本 | 次日开盘卖出 | t | 胜率 |
| --- | --- | --- | --- | --- |
| 换手板 · 概率<30% | 914 | +1.49% | 7.3 | 59% |
| 换手板 · 概率 30~55% | 416 | +1.92% | 6.2 | 67% |
| 换手板 · **概率≥55%** | 257 | **+2.78%** | 6.3 | 65% |

概率在打板口径上单调有效，且 2 月到 9 月**每个月都是正的**（+0.68% ~ +1.56%）。概率≥55% 的票平均 2.5 只/天。

旧版曾提出的待验证用法（不作为当前推荐操作）：

1. 09:25 用概率筛出「今天可能封板」的票（≥55% 进重点池）
2. 盘中这些票真的封板时，在涨停价买入
3. 次日开盘卖出

**必须知道的风险**：换手板只是「当天开过板、理论上能成交」的代理，真实成交率取决于封单量和排队顺序；
一字板那 +6.27% 正是买不到的高收益样本，不能计入可实现收益。上面所有数字均未扣手续费（双边约 0.1~0.2%）。

### 具体案例：合格档 + 竞价未封板 → 竞价买入

140 个交易日里有 772 次「合格」（概率≥55%），其中 **576 次在竞价就一字封板、根本买不到**，
真正可买的只有 196 次（覆盖 92 天）：

| 指标 | 数值 |
| --- | --- |
| 当日收盘涨停（封板） | **43.4%** |
| 当日盘中触及涨停 | 60.2% |
| 胜率（次日开盘价 > 买入价） | **44.9%** |
| 胜率（次日收盘价 > 买入价） | 45.4% |
| 平均收益（次日开盘卖，按笔 / 日等权） | **-1.56% / -0.73%**（t=-0.86） |
| 盘中最大浮盈 / 最大浮亏 均值 | +2.49% / -6.79% |

结果高度两极分化，而这正是亏钱的原因：

| 分组 | 占比 | 当日收盘卖 | 次日开盘卖 |
| --- | --- | --- | --- |
| 当天封住 | 43.4% | +2.59% | +5.77% |
| **没封住** | **56.6%** | **-5.49%** | **-7.17%** |

这批票的当日开盘价平均比昨收高 **+9.04%**——买入时就已经把「可能封板」的预期付掉了，
所以 43% 的封板率也补不回 57% 那部分的亏损。按月看也不稳定：4 月 +2.76%、5 月 -0.25%、
6 月 -2.47%、7 月 -2.13%、8 月 +0.58%、9 月 -3.35%。

**对照**：同样这 772 次「合格」，如果在竞价已经封板时也能买到，次日开盘卖出胜率 60.4%、平均 +1.51%（t=2.93）。
再次说明「合格」这个信号本身是有效的，被吃掉的是竞价买入这个入场价。

复现：`npx tsx scripts/qualified-buy-backtest.ts [概率阈值]`

### 模型还有提升空间吗

试过再加 5 个特征（近 10 日涨停次数、涨停簇跨度、昨日炸板率、大盘 5/20 日涨幅）、4 个非线性项
（竞价接近涨停、竞价≥7%、低开、竞价×连板）以及 3 个位置特征（20 日涨幅、距 60 日高点、昨日振幅），
走前验证 AUC 分别是 0.8071 / 0.8072 / 0.8113，都没有超过现有 8 特征模型的 0.8132：

```text
B 当前线上 8 特征          0.8132
C +涨停历史/情绪/大盘趋势   0.8071
D C + 非线性项             0.8072
E D + 位置特征             0.8113
```

结论：**09:25 这个时点的信息已经被现有特征吃满**，继续堆特征只会过拟合。要再提升应当换时点
（例如引入盘中封单量、开板次数等 09:25 之后才有的信息），而不是继续加日线衍生特征。

### 数据源与稳定性

`push2.eastmoney.com` / `push2his.eastmoney.com` 在部分网络下会被上游直接断连（`other side closed`），
而 `push2ex`、腾讯行情不受影响。因此所有关键数据都做了备用源：

| 数据 | 主源 | 备用源 |
| --- | --- | --- |
| 09:25 竞价明细（竞价价 + 量能） | 腾讯 `stock.gtimg.cn` 分笔 | 东财 push2 → **push2delay**（同一份数据的镜像） |
| 交易日历 | 腾讯指数日K | push2his 日K → 按日期回扫涨停池 |
| 大盘竞价缺口 | 腾讯 `qt.gtimg.cn`（上证今开/昨收） | push2 单只行情 |
| 竞价价（腾讯分笔拿不到时） | 东财 ulist | 腾讯 `qt.gtimg.cn` |

> 行情页（`/api/quotes`、`/api/market-overview`）的选源依据、实测数据与改造结论见上文
> [行情源：腾讯优先，东财兜底](#行情源腾讯优先东财兜底)。

- **竞价成交的时间戳不总是 09:25:00**：实测约三分之一个股戳在 09:25:01~09:25:59
  （例如 2026-09-17 的澳弘电子是 `09:25:01`）。09:25:00~09:29:59 之间不存在连续竞价成交，
  因此取这个窗口内的第一条作为竞价成交，而不是写死匹配 `09:25:00,`
- **按源熔断**：东财明细链上某个源连续失败到阈值后，本次请求不再碰它但继续用镜像；
  全部源都挂掉时直接跳过剩余个股，避免对 80~90 只票逐个空转重试
- 逐笔明细接口只在传输失败时重试（最多 3 次）；上游给出合法响应后不再重试，避免把「没有 09:25 成交」误判成故障
- 详情抓取并发从 8 降到 4，减少上游限流
- 效果：主源被断连时，一次竞价请求从 **25.5s / 量能 0 只 / 每只缺 1 个模型特征**，
  先变成 **3.1s / 量能 89 只**（加 push2delay 镜像），再变成 **2.3s / 量能 89 只**（腾讯分笔做主源）
- `/api/auction` 按交易日缓存 5 分钟：09:25 快照当天不变，缓存既保证同一时段反复刷新看到同一份判定，也避免一次刷新打 80~90 个上游请求
- 只缓存成功结果，失败结果留给下次请求重试

### 竞价分笔：主源已换成腾讯

`stock.gtimg.cn/data/index.php?appn=detail&action=data&c=sh600519&p=0` 返回当日分笔
（`序号/时间/价格/涨跌/成交量(手)/成交额(元)/方向`，70 条一页，`p=0` 就是开盘最早那一段）。
用它和东财 `push2delay` 明细逐只对比：**89 只里竞价首笔价格 0 错、量能最大相对误差 0.011%**
（东财是估算值，腾讯才是真实成交额，所以以腾讯为准）。

端到端跑完整条链路（同一候选池 89 只）：

| 链路 | 墙钟耗时 | 有竞价价 | 有量能 |
| --- | --- | --- | --- |
| 旧：东财明细优先（主源被断连时先重试再切镜像） | 3.5 ~ 6.2s | 89 | 89 |
| 旧：全部分笔走腾讯（`scripts/auction-source-compare.ts` 的对照实现） | 1.6 ~ 2.0s | 89 | 89 |
| **现：腾讯分笔主源 + 东财兜底**（实测 `/api/auction`） | **2.3s** | 89 | 89 |

实现上有两点值得记：

- **先取批量行情，再逐只取分笔**：行情里的**今开就等于 09:25 竞价成交价**（开盘价由集合竞价撮合产生），
  两个批量请求就能覆盖全部候选，分笔只用来补「竞价成交额」
- **护栏用「今开 > 0」而不是本机时钟**：09:25 之前今开是 0，而分笔这时还在吐**上一交易日**的数据。
  用数据自身判断「今日是否已开盘」，不依赖机器时区与时间是否准确；今开为 0 时直接退回东财明细链，
  那条链在 09:25 前会诚实地返回「缺少 09:25 竞价成交数据」

**腾讯分笔拿不到量能时**（例如北交所个股，两家分笔都返回空）仍返回竞价价，量能标记为缺失——
量能是展示项，不影响概率与档位；这也是为什么不再为它回头重试东财。

两家分笔都只覆盖**最近一个交易日**：东财 `details/get` 的 `date` 参数被上游忽略
（实测传 `date=20260910` 与不传返回完全相同的当日数据），所以按历史日期请求竞价时，
候选池是历史快照、而竞价价只能来自最近的交易时段——这个限制在换源前后一致。

## 自选 / 持仓页的「分时图」列

表头顺序是 **股票 / 分时图 / 最新价 / …**，画的是当日 09:30~11:30 与 13:00~15:00 的逐分钟价格。

- **纵轴是相对昨收的百分比**，昨收固定在纵向中点并画一条灰色虚线基准。
  不这么做的话，`8.20→8.25` 的横盘和 `8.00→8.80` 的主升浪会被自适应缩放画成一模一样的坡度，
  一屏 20 行之间就没有可比性了 —— 而这一列的价值恰恰在横向比较。
- 纵轴虽然按行自适应，但**量化到固定档位**（1/2/3/5/8/10/15/20/30%）：既不会把 ±0.2% 的横盘噪声
  拉满整幅，也顺带解决了「全部同价」时的除零问题。
- 颜色只表达**末点相对昨收的方向**（涨红跌绿，与右边涨跌幅列同一套语义），不做分段染色 ——
  240 段在 96px 宽里平均不到 0.4px，分段染色只会退化成一条红绿噪点带。
- 与昨收持平时是中性灰、线压在基准虚线上；缺昨收时不画基准线、也不假装知道涨跌；
  没有分时数据（停牌等）显示「—」。涨停一字板会如实贴顶，**不会为了好看而缩放**。
- **刻意没画的**：均价线（26px 高两条线会绞在一起，且需要每分钟累计成交额）、坐标轴/刻度、
  填充与阴影。

数据来自 `/api/minute`（腾讯 `ifzq.gtimg.cn` 分时，**一次一只票**）：

- 请求数 = 票数，比 `/api/quotes` 贵得多，所以它**不跟 10 秒行情轮询**，只在
  ① 首次加载 / 自选·持仓的代码集合变化、② 从其它标签页切回来（最小间隔 5 分钟，`MINUTE_REFRESH_MIN_MS`）时取
- 单只票只失败那一行，显示「—」，不抛错、不影响行情与其它列

### 主线：收盘后固定动作（页面默认档）

后端在 `server/mainline/`，接口 `/api/mainline?days=N&date=YYYYMMDD`；
CLI 用 `npm run mainline`（默认回看 5 个交易日，写 `data/mainline/<日期>.md`）。
判定规范与完整设计见 **[主线引擎设计稿](docs/mainline-engine-design.md)**。

页面四段对应四个动作：

1. **四榜并列** —— 涨幅 / 涨停家数 / 主力净流入 / 成交额，各 Top 10，每行标「连N」；
2. **反复出现的板块** —— 连续 3 天以上在同一个榜的前列（任一榜，不是「多榜同时」）；
3. **当日板块总览** —— 得分 / 分档 / 涨停 / 连板 / 最高板 / 四榜名次 / 连榜 / 连续；
4. **重点板块明细** —— 五档阵容（高度龙头 · 前排核心 · 中军 · 首板助攻 · 完整梯队）
   + 从板块里提取的题材（涨停原因归一后 ≥2 家成题，带连续天数与跨板块扩散）
   + 逐日轨迹 + 评分逐项依据。

**口径与限制**（页面「数据说明与限制」里逐条写着，这里同步一份）：

- 板块宇宙 = 同花顺涨停板块 **Top 20 的历史并集**（`block_top` 单日只给 20 个，参数无效）。
  从没进过 Top 20 的板块不在表内——**这是口径限制，不是「今天没有主线」**。
- 「上榜」门槛 = 当日池子的**前 25%（上限 10 名）**。原方法的「前 10」是按全市场几百个板块
  说的；20 个板块的池子里直接套用会松到没有区分度（实测 8 个交易日里没有任何板块能连续
  3 天进两个榜的前 10）。
- **历史日没有资金流**：`realhead` 没有历史接口，板块年度日K 里也没有资金流列。
  所以主力净流入榜只在最新交易日有值；历史上的「分歧后回流」只用涨幅与涨停家数判定。
- 中军的「大成交」用「**流通市值 × 换手率**」近似（涨停池不给成员当日成交额），属代理口径；
  完全算不出来时显示「不可判定」，**不会显示成「没有中军」**。
- **加载状态与「没有数据」是分开的**：5 天窗口实测约 7 秒（要拉这几天的涨停板块、涨停池
  与板块实时行情），这期间显示「正在拉取主线数据」，只有真的取完了才可能说没数据。
- 评分**不是买卖信号**，用于防止被当天涨幅迷惑。

**实测脚本**（只读公开接口，不写文件）：`tmp-analysis/mainline-*.mjs`、
`tmp-analysis/ths-only-probe*.mjs`、`tmp-analysis/tag-distribution.mjs`。

### 趋势：形态扫描（**不是选股信号**）

按用户口径扫描「5/10/20 日线多头 + 连续站稳 5 日线 + 回调缩量 + 距 5 日线 ≤4% + 近期涨幅 ≤20%」，
候选范围固定全市场，条件全部可调，另有「至少满足条件数」档（5/5、4/5、3/5）
用来看「差一点」的票——未命中的条件会逐条列出来。

**扫描深度可切三档**（表单里的「拉日K上限」）：`260 只`（默认快速，约 7 秒）、`1000 只`、`全部`。
「全部」按当日成交额从高到低把全市场（约 5900 只）的日K都拉完，首次实测约 36 秒，
期间页面停在「扫描中…」；个股日K 有 10 分钟缓存，期间重扫只补没拉到的部分。
无论哪一档，页面都如实披露「扫描范围 N 只 · 已拉日K M 只（成功 / 失败） · 未扫描 K 只」，
命中数一律限定在已扫描范围内——**没扫到的部分不会假装扫完了**。

**页头固定显示回测结论，这不是装饰文案。** 这套形态被本项目回测否定，而且方向与直觉相反
（`scripts/screener-trend-backtest.ts`，114 个交易日 / 5532 只票，超额口径为「相对当日全市场等权」）：

| 组 | 次日开盘 | T+1 | T+10 |
| --- | --- | --- | --- |
| 全市场 ∩ 形态 | −0.141%（t=−2.56） | −0.084% | −1.440%（t=−3.28） |
| 主线板块 ∩ 形态 | −0.162%（t=−2.60） | −0.258% | −1.788%（t=−3.73） |
| 配对检验：加「主线」过滤 | — | **−0.173%（t=−2.53）** | −0.349%（t=−2.29） |

归因（在主线池里逐条加条件，超额相对全市场）：

| 条件阶梯 | 次日开盘 | T+10 |
| --- | --- | --- |
| 主线池全部（不加形态） | +0.002% | **+0.084%** |
| ＋MA5>MA10>MA20 | **−0.127%（t=−2.01）** | **−2.426%（t=−2.25）** |
| ＋连续站稳 5 日线 | −0.204%（t=−2.61） | −1.935% |
| ＋距 5 日线 ≤4% | −0.208%（t=−2.90） | −2.129% |
| ＋近 10 日涨幅 ≤20% | −0.167% | −2.535% |
| ＋回调缩量（完整形态） | −0.021%（t=−0.97） | −1.788%（t=−3.73） |

**毒源是「均线多头」这一个条件**；「回调缩量」是唯一有正面作用的条件，但救不回整体。
所以这个页面的定位是**看懂形态分布**，不是挑能买的票。

复现：`npx tsx scripts/screener-trend-backtest.ts` →
`scripts/output/screener-trend-backtest.log` / `.json`。

  前四个来自 `block_top`，**封单 / 开板 / 换手 / 流通来自当天同花顺涨停池**（按代码 join，实测 18/18 命中），
  补不到的票显示「—」，不拿别的数字顶；
- **默认排序 = 连板高度 → 首封时间 → 封单额**，并在表里标出「板块内最高板」那一档。
  这是**描述谁更强**的机械口径，页头写明了它不是推荐、也不代表次日会涨；
- **点一行可展开**，展开的是涨停原因长文（同花顺 `reason_info`，AI 汇总稿，含公告依据）。
  这个口径里没有「判断明细」那套东西，所以展开里不编它；
- 缺失一律按缺失展示（`metricsState: 'missing'`、`risksChecked: false`、`relation.state: 'unknown'`）。

#### 细分逻辑：当日涨停原因标签

「板块」档回答的是「涨停集中在哪些**板块名头**下」，宽概念天然占优；
真正回答「今天在炒什么」的是**涨停原因标签**词频。

| 项 | 口径 |
| --- | --- |
| 上游 | 同花顺涨停池 `reason_type`（涨停原因标签，如「上海国资」「人形机器人」） |
| 单位 | 归一化后的标签本身，家数 ≥2 才成题 |
| 主线 | 当日家数 ≥5 且前两日各 ≥2；不满足则支线 |
| 接口 | `GET /api/themes?date=YYYYMMDD`（`buildTopics`） |

**它经常显示「主线 0 个」，那不是 bug 而是结论**：今天最强的标签也只有 2~3 家
（2026-09-18：上海国资 3 / 海峡两岸 3 / 人形机器人 2），够不上主线门槛——
也就是说当天**没有一条集中且连续的逻辑**。三张榜里只有这一张能得出这个结论。

代价也要说清：同一只票的多个标签各自成题，家数天然比板块口径小，
所以它的「主线」比板块口径稀疏得多；该口径**尚未回测**，只作结构观察。

三档的关系（同一时刻，2026-09-18）：

```text

轮动（财联社 30 天）    芯片产业链 / PCB / 光通信                ← 最近谁反复领涨
```

实测（2026-09-18）：

三家板块名的重合度（2026-09-18 实测）：同花顺 Top 20 里，东财有同名板块的 **14/20**、

也就是说**跨源合并板块是不可行的**——同名不等于同一批成分股，家数放一起就是两套口径混着读
（当初否决「跨源题材合并」的理由在这里同样成立）。

### 题材：细分逻辑（接口保留口径，页面已不用）

> 细分逻辑口径仍留在后端 `/api/themes`（`buildTopics`），页面不再使用；
> 下面是它的口径与当初换掉东财板块的理由，保留备查。

**细分逻辑的单位是涨停原因标签，不是东财宽概念板块。**

> 板块轮动与财联社情绪**不在这里** —— 它们是独立的一级页「轮动」
> （见 [轮动：板块轮动与市场情绪](#轮动板块轮动与市场情绪)）。
> 那是历史板块口径，与下面的当日主线 / 支线不是同一套东西（板块划分与家数都对不上），
> 混在一屏容易被当成同一口径读。

| 口径 | 含义 |
| --- | --- |
| 题材 | 归一化后的涨停原因标签（如「光通信」「先进封装」「上海国资」），家数 ≥2 才成题 |
| 家数 | 当日涨停原因含该逻辑的涨停股数（同一天同一标签，同一只票只算一次） |
| 持续性 | 各交易日**当日**涨停原因统计出的家数序列（含当日，新到旧） |
| 主线 | 当日 ≥5 且前两日各 ≥2；不满足则支线 |
| 成员 | 当日涨停原因含该逻辑的股票；所属板块只作为参考标签 |

当初换掉板块口径的理由（页面现在又用回板块，这段保留备查）：

- **宽概念的家数 = 子题材并集**。2026-09-18 实测「半导体概念 11 家」中，国产芯片 8、
  存储芯片 5、先进封装 4、汽车芯片 2——11 家不是 11 只票在炒同一件事；当天「华为概念 13 家」的
  涨停原因分别是 800G交换机 / 液冷服务器 / 清洁机器人 / AI安全 / 抗量子密码…，彼此无关。
  按板块家数排名**必然**选出这种凑数的宽概念。
- **不做同族合并**。「清洁机器人 + 机器人结构件 + 环卫机器人 → 机器人 6 家」等于在标签层
  再造一次宽概念；每个原始标签各自成题。
- **通用词不成题材**：业绩增长 / 半年报增长 / 定增 / 回购 / 控制权变更 / 订单…（见
  `GENERIC_TOPIC_WORDS`）只说明公司行为，不说明题材。
- **没有前视偏差**：板块口径用「当前成分股」回算历史涨停家数，等于用后见之明判断当时的持续性；
  细分逻辑口径直接用各交易日的涨停原因，是当时就能看到的信息。
- 成交额 / 板块涨幅 / 指数超额依赖板块日K，题材口径下没有来源，一律标「不可用」，不拿别的数字顶。

实测对照（2026-09-16，宽概念 vs 细分逻辑）：

```text
宽概念口径（家数最多的几个）   细分逻辑口径（家数最多的几个）
央国企改革 23 家              光通信 5 家
通信技术 18 家                半导体设备 4 家
锂电池概念 18 家              AI算力 3 家、海峡两岸 3 家、福建国资 3 家
半导体概念 18 家              存储芯片 2 家、高端PCB 2 家、高速光模块 2 家
```

接口：

```text
GET /api/themes/ths?date=YYYYMMDD          # 同花顺板块（Top 20）：选股页「板块」档用这个
GET /api/ths-boards/:code/detail           # 同花顺板块成员（code 是 5~6 位数字）
GET /api/themes/boards?date=YYYYMMDD       # 东财板块（宽概念）口径：接口保留，页面不再用
GET /api/themes/:code/detail               # 东财板块详情（BK 代码）
GET /api/themes?date=YYYYMMDD              # 细分逻辑口径（接口保留，页面不再用）
GET /api/topics/:key/detail?date=YYYYMMDD  # 细分逻辑详情（key 是标签，注意 URL 编码）
```

细分逻辑口径的成员表只给涨停池字段（连板 / 首封 / 封单 / 换手 / 流通市值 / 涨停原因），
**K线形态、角色标签、风险核验尚未在细分逻辑口径接入**，按缺失披露；这套能力只挂在东财板块口径上。

东财板块口径（宽概念）的 v2 规则如下（接口保留、页面不再用，留作对照）：

- 取最近 3 个交易日（按交易日历判相邻，跨周末/节假日算连续）；
- **主线 = 当日概念家数排名前 3 名**，且当日概念成员涨停 ≥5、前两日各 ≥2，且不是宽口径属性板块；
- 家数达标但排名在名额外 → 支线；家数数据不足 → 待确认；
- 板块宽度 > 1500 的统计属性板块整块剔除；800~1500 的宽口径题材保留但标注，且不占主线名额。

4 个角色标签（**主线龙头 / 主线换手核心 / 主线趋势中军 / 主线低位补涨**）与逐条命中/未命中
明细只挂在**东财板块口径**的详情上（形态与量能指标依赖板块成分股日K）；细分逻辑详情
暂不提供这些标签，同花顺口径也没有这一套。

### 数据源与稳定性

`push2.eastmoney.com` / `push2his.eastmoney.com` 在部分网络下会被上游直接断连（`other side closed`），
而 `push2ex`、腾讯行情不受影响。因此所有关键数据都做了备用源：

| 数据 | 主源 | 备用源 |
| --- | --- | --- |
| 09:25 竞价明细（竞价价 + 量能） | 腾讯 `stock.gtimg.cn` 分笔 | 东财 push2 → **push2delay**（同一份数据的镜像） |
| 交易日历 | 腾讯指数日K | push2his 日K → 按日期回扫涨停池 |
| 大盘竞价缺口 | 腾讯 `qt.gtimg.cn`（上证今开/昨收） | push2 单只行情 |
| 竞价价（腾讯分笔拿不到时） | 东财 ulist | 腾讯 `qt.gtimg.cn` |

> 行情页（`/api/quotes`、`/api/market-overview`）的选源依据、实测数据与改造结论见上文
> [行情源：腾讯优先，东财兜底](#行情源腾讯优先东财兜底)。

- **竞价成交的时间戳不总是 09:25:00**：实测约三分之一个股戳在 09:25:01~09:25:59
  （例如 2026-09-17 的澳弘电子是 `09:25:01`）。09:25:00~09:29:59 之间不存在连续竞价成交，
  因此取这个窗口内的第一条作为竞价成交，而不是写死匹配 `09:25:00,`
- **按源熔断**：东财明细链上某个源连续失败到阈值后，本次请求不再碰它但继续用镜像；
  全部源都挂掉时直接跳过剩余个股，避免对 80~90 只票逐个空转重试
- 逐笔明细接口只在传输失败时重试（最多 3 次）；上游给出合法响应后不再重试，避免把「没有 09:25 成交」误判成故障
- 详情抓取并发从 8 降到 4，减少上游限流
- 效果：主源被断连时，一次竞价请求从 **25.5s / 量能 0 只 / 每只缺 1 个模型特征**，
  先变成 **3.1s / 量能 89 只**（加 push2delay 镜像），再变成 **2.3s / 量能 89 只**（腾讯分笔做主源）
- `/api/auction` 按交易日缓存 5 分钟：09:25 快照当天不变，缓存既保证同一时段反复刷新看到同一份判定，也避免一次刷新打 80~90 个上游请求
- 只缓存成功结果，失败结果留给下次请求重试

### 竞价分笔：主源已换成腾讯

`stock.gtimg.cn/data/index.php?appn=detail&action=data&c=sh600519&p=0` 返回当日分笔
（`序号/时间/价格/涨跌/成交量(手)/成交额(元)/方向`，70 条一页，`p=0` 就是开盘最早那一段）。
用它和东财 `push2delay` 明细逐只对比：**89 只里竞价首笔价格 0 错、量能最大相对误差 0.011%**
（东财是估算值，腾讯才是真实成交额，所以以腾讯为准）。

端到端跑完整条链路（同一候选池 89 只）：

| 链路 | 墙钟耗时 | 有竞价价 | 有量能 |
| --- | --- | --- | --- |
| 旧：东财明细优先（主源被断连时先重试再切镜像） | 3.5 ~ 6.2s | 89 | 89 |
| 旧：全部分笔走腾讯（`scripts/auction-source-compare.ts` 的对照实现） | 1.6 ~ 2.0s | 89 | 89 |
| **现：腾讯分笔主源 + 东财兜底**（实测 `/api/auction`） | **2.3s** | 89 | 89 |

实现上有两点值得记：

- **先取批量行情，再逐只取分笔**：行情里的**今开就等于 09:25 竞价成交价**（开盘价由集合竞价撮合产生），
  两个批量请求就能覆盖全部候选，分笔只用来补「竞价成交额」
- **护栏用「今开 > 0」而不是本机时钟**：09:25 之前今开是 0，而分笔这时还在吐**上一交易日**的数据。
  用数据自身判断「今日是否已开盘」，不依赖机器时区与时间是否准确；今开为 0 时直接退回东财明细链，
  那条链在 09:25 前会诚实地返回「缺少 09:25 竞价成交数据」

**腾讯分笔拿不到量能时**（例如北交所个股，两家分笔都返回空）仍返回竞价价，量能标记为缺失——
量能是展示项，不影响概率与档位；这也是为什么不再为它回头重试东财。

两家分笔都只覆盖**最近一个交易日**：东财 `details/get` 的 `date` 参数被上游忽略
（实测传 `date=20260910` 与不传返回完全相同的当日数据），所以按历史日期请求竞价时，
候选池是历史快照、而竞价价只能来自最近的交易时段——这个限制在换源前后一致。


## 轮动：板块轮动与市场情绪

一级导航里的独立页（在「选股」之前），左栏**板块轮动**、右栏**市场情绪**。
两者都来自财联社，都不需要任何凭据；前端取数走 `/api/themes/rotation` 与 `/api/market-overview`。

**为什么单独开一页**：轮动是**历史板块口径**，选股页的题材是「当日涨停原因细分逻辑」——
板块划分不同（财联社概念 vs 东财板块 / 同花顺涨停原因），家数无法直接对齐，
放在同一屏容易被当成同一口径读。

### 板块轮动（左栏）

近 **4 / 30 个交易日每日涨幅前 10** 的板块，按「进入 top10 的次数 → 最近上榜日 → 涨幅」排序，
页面默认展示前 12 个。这是本项目**唯一的历史板块口径**：题材总览只有当日快照，回答不了
「这个题材是第几天走强」；轮动是逐日快照，天然没有前视偏差。

- 上游 `/v2/quote/a/plate/rotation` **只支持 `days=4` 与 `days=30`**，
  传其它值上游会回 `{"days":"支持 4/30"}` 这种非数组对象，所以后端直接按 400 挡掉；
- 该接口**没有日期参数**，返回它自己的最近窗口，与页面上正在查看的交易日无关；
- 财联社板块代码（`cls*****`）与东财 `BK****` / 同花顺题材**没有现成映射**，
  所以这一页只展示板块名与涨跌幅，不做跨源题材合并。

### 市场情绪（右栏）

封板率 / 高开率 / 获利率 / 市场热度 / 昨涨停今表现 / 两市成交额 / 连板梯队（各档家数与连板率）。

这几个指标本项目的自算口径（`server/market/breadth.ts` 的涨跌家数 / 涨停 / 炸板 / 晋级率）拿不到 ——
自算它们需要「昨日涨停池」，而东财涨停池**只保留约 15 个交易日**。

- **只有当天实时快照，没有历史**：接口没有日期参数，所以这一页**不提供日期选择**，
  页头的「交易日」就是取数当天；
- 大盘概览（自选 / 持仓页）的「两市成交」卡里也会带一行这几个指标，同样只在当天有值；
- 按历史日期请求 `/api/market-overview` 时后端**不抓**情绪、该字段为 `null`，
  避免把「今天的封板率」贴到历史日期上；
- 口径别混：**封板率** = 最终封住 ÷ 触及涨停，**连板率** = 该板位晋级到下一板的比例。

## 涨停聚焦：涨停池 / 冲刺涨停 / 今-昨对比 / 连板天梯

「涨停聚焦」一级页里有四个子页签（顺序即页签顺序，冲刺涨停紧跟涨停池）：
涨停池、冲刺涨停看的是各自独立的池子，今/昨对比与连板天梯看的是**同一份涨停池**的两个角度。

| 页签 | 看什么 | 数据 |
| --- | --- | --- |
| 涨停池 | 逐票明细（连板 / 板块 / 封板时间 / 炸板次数），行尾可直接「添加自选」 | `/api/limit-up` |
| 冲刺涨停 | 强势股池（还没封板但接近涨停的票） | `/api/sprint-limit-up` |
| 今/昨对比 | 一个**昨日板位**一块：块头给这一档的家数与晋级率，块内上半是今天晋级到下一板位的瓷砖、下半是没继续涨停的瓷砖（同一只票只出现一次）；所有涨跌幅都是**今天**的实时值 | `/api/limit-up-ladder` + `/api/quotes` |
| 连板天梯 | 今日池子按**今日板位**分层（5 板 / 4 板 / … / 首板）+ 晋级率 | `/api/limit-up-ladder` |

今/昨对比与连板天梯**共用一次请求**：两个视图本来都要昨日池子
（天梯的「晋级率」也是「昨日涨停今天再涨停 / 昨日涨停」），分两个接口只会把同一份池子拉两遍。
所以切这两个页签不会重复打上游，页面停在涨停池时则一次都不打。

几个口径上的决定：

- **上一交易日按交易日历取**（腾讯上证日K，`fetchTradeDatesUpTo`），不按自然日回溯——周一要跳到上周五。
  日历拿不到时退回「按自然日回扫」兜底，但**只认真的拿到非空涨停池的那一天**，
  所以假期里的空池会被自动跳过，不会把节前最后一天当成「昨天」
- **今日连板数由池子自带**（`lbc`），不自己用「昨日板数 + 1」推算；
  昨天 3 板今天涨停就显示 4 板，两个口径不会在同一个页面上打架
- **昨日池子没取到时只降级一半**：今日天梯照常给，晋级率与对比显示 `—` 并写明原因。
  这种情况 `status` 仍是 `fresh`、`error` 仍是 `null`——`error` 的语义是「这份响应本身有问题」，
  用它去描述「昨日那一半没取到」会让前端把整份今日天梯一起当成坏数据；
  缺失由独立的 `previousAvailable` 字段表达。**绝不用 0% 冒充「没取到」**
- **对比只回答「昨天的票今天怎么样了」**：今天新进池子的票不在对比里；
  一档就是昨日同一个板位的**全部**涨停股，块内再按「今天晋级到下一板位 / 没继续涨停」分成上下两组，
  同一只票只出现一次；两组的涨幅都是**今天**的实时涨跌幅——断板那批不在今日涨停池里，
  它们的今日涨幅单独走 `/api/quotes`（`comparisonQuotes`），拿不到行情就显示 `—`，
  **不拿池子里昨天那根涨幅冒充今天**
- **盘前/非交易日自动落到最近一个有数据的交易日**：上游在请求日还没有池子时，
  会把最近一个交易日的池子原样返回、`tradeDate` 只是请求日期的回显，
  此时「今天」和「昨天」是同一份快照（比出来是假的 100% 晋级、断板全无）。
  所以两份池子的代码与连板数完全相同时，把「今天」落到那个交易日、再往前取它的上一日当「昨日」，
  页面顶部也会写明「今天还没有涨停池数据，下面是最近一个交易日 X 的对比」
- 连板天梯默认只展开**最高板**：天梯全展开时一行行看下来反而看不出层级
- 上游没给连板数（`lbc` 缺失）的票单独成「连板未知」一档、排在最后，不冒充首板

复现：`npx tsx scripts/_ladder-probe.ts 20260917` 直接打上游跑一遍计算，
打印今日/昨日天梯与逐档晋级明细（2026-09-17 实测：今日 47 只 = 5 板 1 / 3 板 3 / 2 板 5 / 首板 38；
昨日 89 只，晋级 9 只，晋级率 10.1%）。

## 股票标识（头像 + 标签）

所有出现股票名的列表（自选、持仓、涨停池、冲刺涨停、右侧冲刺涨停侧栏、竞价、龙虎榜）
统一用设计稿 F 的标识：名称左边是首字头像方块（沪市 `6` 开头蓝色、深市/北交所绿色），
名称右边是红底红字的小标签（`.stock-tag`）。标签内容按列表取该行最该被看到的信息：

| 列表 | 标签内容 |
| --- | --- |
| 自选 / 持仓 | 备注（`note`）+ 涨停标识：有备注时备注是红色主标签、涨停退成蓝色副标签；没备注时涨停标识自己当红色主标签（首板写「涨停」，2 板以上写「N 连板」） |
| 涨停池 | 无标签（连板数已在「连板」列，名称旁不再重复挂标签） |
| 今/昨对比 | 无标签（整档就是同一个板位，涨幅列已经分色） |
| 连板天梯 | 无标签（整档就是同一个板位，逐票再挂一次是重复） |
| 冲刺涨停（表格 + 右侧侧栏） | 涨停次数，如 `2 次`；右栏窄，次数为 0（还没封板）时不挂标签，完整次数看整页 |
| 竞价候选 | 昨日连板数，如 `2 连板` |
| 龙虎榜 | 上榜原因前 8 个字，完整原因仍在「上榜原因」列 |

自选/持仓的涨停标识来自**当天涨停池**（`/api/limit-up` 的 `lbc` 连板数，见
`src/lib/limitUpInfo.ts`），所以只有「今天封在涨停价」的票才有这个标签；
池子不可用时返回空表、不会清掉已有标签。自选/持仓页进入时会拉一次池子，
之后复用同一份数据，不额外增加请求。

组件在 `src/components/StockIdentity.tsx`，样式是 `src/styles.css` 末尾的
`.stock-identity* / .stock-tag / .stock-tag--secondary`（放在末尾是为了稳定压过
各列表自己的字号规则）。

## 回测与验证脚本

`scripts/` 下的脚本用于训练和校验模型，不参与构建：

```text
scripts/limit-up-history.ts     用日K自建涨停历史（新浪，140 个交易日、全市场 5500 只）
scripts/auction-model.ts        训练/验证涨停概率模型，输出系数与校准表
scripts/limit-up-hold-analysis.ts 入场口径对比：竞价买入 vs 打板买入、成交可行性与稳定性
scripts/qualified-buy-backtest.ts   「合格 + 竞价未封板 → 竞价买入」的胜率回测
scripts/watch-signal-lab.ts        买强类条件的验证（42 万样本，结论：无效甚至反向）
scripts/watch-timing-lab.ts        择时类条件的验证（39 万样本 × T+1/T+2/T+3）
scripts/watch-rank-lab.ts          市值/价格/波动/动量分位检验 + 市场择时
scripts/watch-ambush-lab.ts        埋伏分构造与样本外验证（输出运行时参数）
scripts/auction-success-rate.ts 当日盘中统计：封板率 / 触板率 / 收益，按概率分组
scripts/auction-stability.ts    连续两次抓取，检查判定是否稳定
scripts/auction-buyable-lab.ts      特征增减实验台（36 个变体 + V3 候选，走前验证）
scripts/auction-buyable-region.ts   结构诊断：涨幅×连板网格、阈值扫描、训练区域收窄
scripts/auction-tier-filters.ts     「较高概率」池上 90 个筛选组合 + 按日 bootstrap
scripts/auction-tier-rules-check.ts 候选筛选规则的 bootstrap 与留出期复核
scripts/auction-gap-rule-check.ts   外部竞价涨幅规则逐档核对
scripts/auction-volume-pilot.ts     早盘量能代理预实验（含量比同时性污染对照）
scripts/fetch-sina-minute.ts        抓新浪分钟K线，用于重建早盘量能代理（注意限流）
scripts/_host-health.ts         上游主机巡检：逐个数据源打点，统计成功率/延迟/错误类型
scripts/source-benchmark.ts     腾讯 vs 东财 同数据对比：交易日历/大盘缺口/批量行情/分笔
scripts/auction-source-compare.ts 竞价链路端到端对比：现状（东财优先）vs 腾讯优先
scripts/_ladder-probe.ts        连板天梯 / 今昨对比直接打上游跑一遍，打印逐档晋级明细
scripts/output/                 数据集、模型参数与原始响应缓存（已 gitignore）
```

行情「大片缺失」时先跑 `npx tsx scripts/_host-health.ts`：能直接看出是某一家整站挂了，
还是单个接口改了字段。2026-09-17 的结论是前者 —— `push2` / `push2his` 全军覆没，其余上游全绿，
据此把行情主源切到腾讯。

为什么自建涨停历史：东财涨停池接口只保留约 15 个交易日，样本量不足以训练概率模型。自建名单已在 2026-09-16 与官方涨停池逐只比对，89 只全部命中（另多 2 只）。

模型自检：`npx tsx scripts/auction-model.ts` 会打印走前验证的 AUC、Brier 和校准表。改动特征或阈值后应当重新跑一遍，不要只看样本内。

外部数据源调研：[thsdk 评估](docs/thsdk-evaluation.md)（第三方逆向封装，结论不引入；
其中提到的同花顺**官方** hithink-finance REST 服务可以补竞价字段与历史涨停池，待确认价格）。

[levistock 评估](docs/levistock-evaluation.md)（Python SDK，结论**不引入包本身**，但从中挑出两个可自建的上游：
财联社**情绪**与**板块轮动**，已落地；开盘红历史涨停天梯留作离线 POC）。

```bash
npx tsx scripts/auction-model.ts          # 训练 + 走前验证 + 输出校准表
npx tsx scripts/auction-success-rate.ts   # 当日盘中统计
npx tsx scripts/_host-health.ts           # 上游健康巡检（行情缺失时先跑这个）
npx tsx scripts/source-benchmark.ts 6 4   # 腾讯 vs 东财 逐接口对比
```
